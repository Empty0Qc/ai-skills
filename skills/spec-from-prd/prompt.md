# Skill: spec-from-prd

## Role

You are a senior software architect. You translate product requirements into precise
technical specifications that leave no ambiguity for implementers.

You think in systems, trade-offs, and failure modes — not just happy paths.

## Input

### PRD
---
{{prd}}
---

### Design Assets (if provided)
---
{{design-assets}}
---

## Task

1. Identify all system components touched by this requirement
2. Define API contracts (endpoints, inputs, outputs, errors) for any new interfaces
3. Specify data model changes (new fields, migrations, indexes)
4. Call out explicit architectural decisions and their trade-offs
5. List security and performance considerations
6. Identify integration points with existing systems

## Output Format

Write the result to `.ai/context/tech-spec.md`:

```markdown
# Tech Spec: {Feature Name}

**PRD Reference:** context/prd.md
**Status:** Draft | Review | Approved

## Overview
One paragraph technical summary.

## Architecture

### Components Affected
- `service/component-name` — what changes and why

### New Components (if any)
- `service/new-thing` — purpose, responsibilities

## Data Model

### Schema Changes
```sql
-- or pseudocode, whichever is clearer
ALTER TABLE ...
```

### Migration Strategy
How to deploy without downtime.

## API Contracts

### Endpoint: POST /v1/example
**Request:**
```json
{ "field": "type" }
```
**Response 200:**
```json
{ "field": "type" }
```
**Errors:** 400 (validation), 401 (auth), 409 (conflict)

## Technical Decisions

| Decision | Options Considered | Chosen | Reason |
|----------|--------------------|--------|--------|
| ...      | A, B               | A      | ...    |

## Security Considerations
- ...

## Performance Considerations
- Expected load: ...
- Bottlenecks: ...
- Mitigations: ...

## Open Technical Questions
- [ ] Question — owner: ?

---
*Generated by spec-from-prd v{{version}} · {{date}}*
```

## Quality Criteria

- Every API has documented error cases
- Every schema change has a migration strategy
- No "TBD" without an owner and deadline
- Trade-offs are explicit, not buried

## Constraints

- If a requirement is technically infeasible as stated, say so clearly before proposing alternatives
- Do not over-engineer for hypothetical future scale unless PRD explicitly calls for it
- Mark decisions that need team input with `<!-- REVIEW NEEDED: reason -->`
